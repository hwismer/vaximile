# nf-core migration notes

The repository was reorganised into the nf-core directory layout without rewriting process
bodies. This file records what changed, what is intentionally unfinished, and the decisions
a future pass needs to know about.

## What changed

- **Entry point.** `vaximile.nf` became `main.nf` (thin entry workflow, `publish:` and
  `output {}` blocks) plus `workflows/vaximile/main.nf` (the named `VAXIMILE` workflow,
  which now `take:`s the parsed samplesheet and capture kit channels and `emit:`s what used
  to be published directly).
- **Samplesheet parsing** moved out of the entry workflow into
  `subworkflows/local/utils_nfcore_vaximile_pipeline/main.nf` as `PIPELINE_INITIALISATION`,
  alongside `PIPELINE_COMPLETION`.
- **Modules.** The 13 grouped files under `modules/local/` were split into 94
  single-process directories, `modules/local/<process_name_lowercased>/main.nf`. Process
  names were left untouched so task tags and `-resume` cache keys are unaffected.
- **Subworkflows.** The 11 files under `workflows/` were split into 17 directories under
  `subworkflows/local/`, one per `workflow` block. `DEEPSOMATIC`, which was defined inline
  in `workflows/deepsomatic.nf`, became a module.
- **Parameter defaults** moved from the top of `vaximile.nf` into `params {}` in
  `nextflow.config`, and are now described in `nextflow_schema.json`.
- **Assets** moved: `example_inputs/` → `assets/`, `misc/vaxsimile_logo.png` →
  `docs/images/`, `envs/mhcflow.yml` → `modules/local/mhcflow/environment.yml` (the module
  previously referenced `./envs/mhcflow.yml`, resolved against the launch directory rather
  than the module, which only worked when launching from the repo root).
- `example_inputs/vax_config_example.nf` → `conf/ucsf_krummellab.config`.

## Duplicate process names

Three process names existed twice with different implementations. Rather than rename the
processes, the module directories were disambiguated:

| Process           | Original file                   | Module directory                        |
| ----------------- | ------------------------------- | --------------------------------------- |
| `FILTER_VCF`      | `germline_variant_calling.nf`   | `modules/local/filter_vcf_germline/`     |
| `POSTPROCESS_VCF` | `germline_variant_calling.nf`   | `modules/local/postprocess_vcf_germline/`|
| `VEP_ANNOTATE`    | `germline_variant_calling.nf`   | `modules/local/vep_annotate_germline/`   |
| `FILTER_VCF`      | `vcf_postprocessing.nf`         | `modules/local/filter_vcf/`              |
| `POSTPROCESS_VCF` | `vcf_postprocessing.nf`         | `modules/local/postprocess_vcf/`         |
| `VEP_ANNOTATE`    | `vcf_preparation_pvactools.nf`  | `modules/local/vep_annotate/`            |

`nf-core lint` expects a local module's directory to match its process name, so it will
flag these. The alternative — renaming the processes — changes task names and invalidates
existing `-resume` caches, which is why it was not done here.

## Intentionally unfinished

Nothing below breaks the pipeline; each is a step toward `nf-core lint` passing.

1. **`task.ext.prefix` is not wired into 27 of the 94 modules.** All 94 now carry a
   `process_*` label and none declares `cpus`/`memory`; 67 support `ext.prefix` and 19
   read `ext.args`. The 27 without `ext.prefix` were skipped deliberately — see
   "Modules that cannot use ext.prefix" below. Giving those renameable outputs means
   changing what the tools are told to write, not just how the outputs are declared.
2. **No `versions.yml`.** No module emits tool versions, so there is no software versions
   table in the MultiQC report.
3. **No `meta.yml` or `environment.yml` per local module.** Conda specs are still inline
   `conda "bioconda::tool=version"` strings, except `mhcflow`.
4. **Software provisioning is split, so no single profile covers the pipeline.** 59 local
   modules declare only a `container`, 31 declare only `conda`, 4 declare neither, and
   none declare both. `-profile conda` therefore cannot resolve the 59, and the container
   profiles cannot resolve the 31; the pipeline has in practice been run with conda and a
   container engine enabled simultaneously. nf-core modules declare both, which is what
   would make the profiles independently usable. The four with neither
   (`combine_fastqs`, `prepare_fasta`, `pull_arriba_resources`,
   `pull_ctat_resource_bundle`) depend on host `PATH`.
5. **`conf/test.config` is a stub.** It points at the example samplesheet, which references
   FastQ files that do not exist, and the pipeline requires a VEP cache. A real CI test
   likely needs to target a subset of the workflow rather than all of `VAXIMILE`.
6. **`nextflow_schema.json` was written by hand** rather than generated by
   `nf-core pipelines schema build`, so it has not been validated against the plugin.
7. **`nf-schema` is declared but not exercised end to end.** `PIPELINE_INITIALISATION`
   calls `validateParameters()` and `paramsSummaryLog()` from `plugin/nf-schema`. The
   modules pass `nextflow lint`, but no pipeline run has reached the point of validating
   real parameters against `nextflow_schema.json`.

## Argument order is not checked by anything

Hoisting flags into `ext.args` collapses them into one place on the command line. When
the hoisted flags were **not adjacent** in the original script, this silently reorders
the command.

That broke `SALMON_QUANT`: `--libType A` was argument 2 and `--validateMappings` was
argument 5, with `-1/-2` between them. Both moved into a single `$args` after the read
files, and salmon refuses a library type that appears after its inputs. The module now
places `$args` ahead of `-1/-2` and says so in a comment.

10 of the other 18 `ext.args` modules also have non-contiguous hoisted flags. They are
fine only because their tools do not care about order — VEP uses `Getopt::Long`, GATK and
GATK3 parse Java-style arguments, bcftools and DeepVariant/DeepSomatic take only
`--flag=value` options, and pVACseq/pVACfuse place `$args` after all five of their
positional arguments.

Before hoisting anything else, check whether the flags were adjacent, and whether the
tool has positional arguments or documents an ordering requirement. Neither `nextflow
lint` nor the conversion's own verification pass catches this — they check directives,
output arity, `emit:` names, globs and prefix/args definitions, not semantics.

## Modules that cannot use ext.prefix

nf-core modules declare outputs as globs (`path("*.bam")`) so that `ext.prefix` can
rename them. A glob is only safe if it cannot also match a file staged as an **input** to
the same process — otherwise the input is silently re-emitted as if it were output. These
27 modules have no safe glob, so their output declarations were left exact.

Three distinct reasons:

**The output shares its suffix with the input** (usually because the process sits in a
chain with its own upstream sibling):

| Module | Collision |
| ------ | --------- |
| `apply_bqsr_gather` | inputs are the scatter's `*_bqsr.bam`; output is also `*_bqsr.bam` |
| `base_recalibrator_gather` | inputs are the scatter's `*_recal_table.table` |
| `annotate_vcf_coverage` | chained to itself three times, so the input is already `*_coverage.vcf` |
| `merge_somatic_vcfs`, `postprocess_vcf`, `postprocess_vcf_germline` | inputs from `FILTER_VCF` are `*_variants.vcf.gz` |
| `vep_filter` | output name is identical to what `VEP_ANNOTATE` produces |
| `phase_vcf_vep` | its `*_vep.vcf` is what `vep_annotate` emits |
| `haplotype_caller_gather_select_variants`, `mutect2_gather_select_variants`, `index_vcf`, `index_final_vcf`, `merge_bams` | output has no literal suffix at all, only a bare extension shared with the input |
| `mhcflow` | output is a bare directory named from meta; the only glob would be `*` |

**The filename is not the process's to choose** — the tool derives it, or it is a fixed
literal: `index_fasta` (`samtools faidx` writes `${fasta}.fai`), `somalier_extract`
(named from the BAM's `SM` tag), `create_bwa_index`, `create_star_index`, `hla_bed`,
`split_intervals`, `strelka`, `strelka_germline`, and the four `pull_*` resource modules.

**No filename to hoist**: `novoalign_hla_fasta` has an empty script block and only
re-emits its inputs.

`somalier_extract` is worth a second look independently of this work: it declares
`${meta.sample_name}.somalier` as its output, but `somalier extract` names the file from
the BAM's `SM` read-group tag. If those ever disagree the process fails on a missing
output.

## What has and has not been verified

Nextflow lives at `~/miniconda3/bin/nextflow` (26.04.6), which is not on a default
non-login `PATH` — worth knowing, since a shell that cannot find it makes all of the below
look unavailable.

Checks that **have** been run and pass:

```bash
nextflow config . -profile test   # whole config tree resolves
nextflow lint .                   # 122 files no errors, 128 pre-existing style warnings
```

Plus two scripted checks written for the reorganisation: every `include` path resolves to a
file that really defines the imported name, and every converted module still declares the
same number of outputs with the same `emit:` names, the same non-resource directives, and a
glob that matches the filename it produced before.

Not yet verified:

- **No task has been executed.** Nothing here proves a tool actually runs.
- `nf-core pipelines lint` **cannot run in this environment** — the installed nf-core is
  broken under Python 3.13 (`ModuleNotFoundError: imghdr`). Needs a current nf-core in a
  Python ≤3.12 env, or a newer release.
- `nextflow inspect . -profile test` needs the container/conda backends to resolve, so it
  has not been completed offline.

The first real test is a `-resume` run against data whose previous output you can diff.
Output filenames were deliberately preserved, so a correct conversion should resume
without recomputing.
